# tests/

Тесты bridge: pytest на **записанных** ответах API, без сети.

## Почему записанные ответы

Мок, написанный из головы, отражает представления автора, а не реальный API.
Тогда TDD фиксирует неправильную схему и создаёт ложную уверенность.

Поэтому в `recorded/` лежат настоящие ответы, снятые с живых инстансов:

```bash
curl -s -H "X-Api-Key: $RADARR_API_KEY" \
  http://localhost:7878/api/v3/qualityprofile \
  > bridge/tests/recorded/radarr-qualityprofile.json
```

Ключи из ответов вычищаются перед коммитом. Проверяется `gitleaks` в
pre-commit.

## Что должно быть покрыто

Из `docs/ACCEPTANCE.md` и `docs/SPEC.md`:

| Случай | Ожидание |
|---|---|
| Фильм уже в Radarr | 200, `status="exists"` — это успех |
| Сериал есть, сезон новый | 200, сезон добавлен к существующему |
| Нет `tvdb_id` в external_ids | 422, внятный текст, НЕ 500 |
| Номер сезона вне диапазона | 422, с перечислением доступных |
| `type="tv"` без `season` | 422, валидация модели |
| `type="movie"` с `season` | 422, валидация модели |
| `tmdb_id` не существует | 404 |
| Radarr недоступен | 502 |
| Неверный API-ключ | 502, текст про авторизацию |
| dev-режим | поиск не запускается НИ ПРИ КАКИХ входных данных |
| Профиль качества не найден | 500, внятный текст |

## Чего тесты проверить не могут

Жёсткие ссылки, границы монтирований, фактические имена файлов после
импорта. Это `checks/` — shell, curl, jq, stat. Разделение намеренное,
см. `docs/ACCEPTANCE.md`.

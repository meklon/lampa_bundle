# PROCESS.md

Как ведётся разработка. Обязательно к исполнению.

---

# 1. Среда

Вся разработка — в отдельной виртуальной машине. На реальный сервер агент
не заходит.

**ВМ должна повторять форму файловой системы сервера:** тот же путь
`DATA_ROOT`, `torrents/` и `media/` на одной файловой системе. Если в ВМ они
на разных монтированиях, проверка жёстких ссылок пройдёт в среде, где баг
физически не воспроизводится, и он всплывёт уже на сервере.

**Снапшот ВМ перед каждым этапом.** Испорченное состояние откатывается одним
движением вместо сеанса отладки. Отдельный снапшот перед любым обновлением
версий *arr: миграции БД односторонние.

---

# 2. Ветки и коммиты

- Ветка на этап: `stage/1-infra`, `stage/2-provision`, `stage/3-pipeline`,
  `stage/4-schemas`, `stage/5-bridge`, `stage/6-plugin`, `stage/7-bundle`
- Ветки идут цепочкой: каждая отходит от предыдущей, потому что этап опирается
  на результат прошлого. Мержатся в том же порядке
- **Пуш только в свою ветку.** `main` не трогать
- В `main` мержит человек. `deploy.sh` тянет только `main`
- Коммиты小 и осмысленные; сообщение отвечает на «зачем», не на «что»
- Перед коммитом проходит `pre-commit`. Ключи в коммит попадать не должны

Если ключ всё же попал в историю — не подчищать историю, а перегенерировать
ключ в веб-морде сервиса. Это две секунды.

---

# 3. Этапы

Строго последовательно. Этап не закрыт, пока не прошли его проверки из
`checks/` (см. `ACCEPTANCE.md`).

## Этап 1 — инфраструктура

`docker-compose.yml`, `scripts/init-data.sh`, `.env`.

Поднять стек, забрать API-ключи из веб-морд, дописать в `.env`, перезапустить.

Проверки: `01-containers.sh`, `02-data-layout.sh`.

## Этап 2 — конфигурация как код

`provision/`.

**Конфигурация *arr выполняется только идемпотентными скриптами через API.**
Не руками через веб-морду и не разовыми curl'ами.

Причина: конфигурация живёт в SQLite внутри `config/`-томов, который в git не
попадает. Настроенное руками не видно в PR, стирается откатом снапшота и не
воспроизводится на сервере.

Требование идемпотентности: повторный запуск `provision.sh` на уже настроенном
стеке не должен создавать дубликаты и не должен падать.

Индексаторы на этом этапе **не добавляются**.

Проверки: `03-prowlarr-sync.sh` (после того как человек добавит хотя бы один
индексатор — до этого пропускается с явным сообщением).

## Этап 3 — конвейер на тестовом торренте

`fixtures/`.

Собрать локальный торрент из открытой короткометражки, добавить в qBittorrent
в категорию `radarr`, убедиться, что Radarr импортировал файл жёсткой ссылкой
с каноничным именем.

**Это ключевой этап.** Здесь проверяется вся инфраструктура без участия
bridge, плагина и сети.

Проверки: `04-hardlink.sh`, `07-pipeline.sh`.

## Этап 4 — схемы API

`scripts/fetch-openapi.sh`, `openapi/`.

Скачать схемы из исходников проектов, записать вместе с версией и коммитом
в `openapi/SOURCES.md`, сверить с версиями живых инстансов.

**Схемы не отдаются по `/api/v3/openapi.json`** — на production-сборках этого
пути нет.

## Этап 5 — bridge

`bridge/`.

TDD: тесты на записанных ответах API, без сети. Имена полей — только из
`openapi/`.

Проверки: `05-bridge-movie.sh`, `06-bridge-season.sh`.

## Этап 6 — плагин

`bridge/static/plugin.js`.

API плагинов Lampa не документирован формально: собранная документация
(`npm run doc`) покрывает только функции с JSDoc, событий карточки там нет.
Поэтому механика берётся **чтением исходников** `yumata/lampa-source`, а
найденное записывается со ссылками на строки — см. `SPEC.md` 3.2.

Проверка — через логи bridge: он пишет каждый входящий запрос вместе с
`origin`.

## Этап 7 — сборка набора

`docker-compose.yml`, `lampac/`, `README.md`.

Этапа не было в первоначальном плане. Он появился, когда выяснилось, что
шести этапов достаточно для работающего конвейера, но **не** для того, что
человек может установить и которым может пользоваться с телефона.

Сюда вошли: Lampac как часть стека (без него телефону некуда ходить за
каталогом), CORS (без него заказ со страницы Lampa блокирует браузер),
установка плагина в `README.md` и выбор профиля качества при заказе.

Признак, по которому этап считается нужным: **человек поднял стек по
README и смог заказать фильм с телефона, не спрашивая автора.**

# 4. СТОП-УСЛОВИЯ

При срабатывании любого: **остановиться, написать отчёт в `reports/`,
прекратить работу.** Не пытаться обойти, не гадать, не подставлять
альтернативу.

## 4.1 Технические

1. Ожидаемого поля нет в схеме `openapi/`
2. Версия схемы не совпадает с версией живого инстанса
3. `stat -c %h` на импортированном файле равен 1 — жёсткая ссылка не создалась
4. `torrents/` и `media/` внутри контейнера на разных устройствах
5. Ответ API не соответствует контракту, описанному в `SPEC.md`
6. Sonarr начал мониторить сезоны, которые не заказывали
7. Radarr добавил фильм, но поиск не стартовал (в prod-режиме)
8. Не удалось получить `tvdb_id` для тестового сериала
9. Требуется отступить от любого инварианта из `CLAUDE.md`

## 4.2 Процессные

10. Проверка из `checks/` не проходит после двух попыток исправления
11. Требуется подключить реальный трекер раньше этапа 6
12. Требуется что-то, чего нет в скоупе (Kodi, Jellyfin, FileFlows и т. п.)
13. Требуется отредактировать `main` или запустить `deploy.sh`

## 4.3 Чего делать нельзя вместо остановки

См. таблицу запрещённых подмен в `CLAUDE.md`. Правило шире таблицы:
**если обход требует отступить от инварианта — это стоп, а не решение.**

# 4.4 Чему научила практика

Не стоп-условия, а привычки, за которые пришлось заплатить отладкой.
Все три — про один и тот же класс ошибок: **успешный ответ не означает
выполненного действия.**

**Состояние читать отдельным запросом, а не из ответа на запись.** Трижды
подряд: `POST /api/v3/series` возвращал `monitored: true`, тогда как в базе
лежало `false`; `POST /api/v3/seasonpass` отвечает `202 Accepted` — «принято»,
а не «применено»; Radarr и Sonarr отдают 500 там, где схема разрешает
отсутствие поля. Проверка результата по телу ответа на запись даёт
ложноположительный результат.

**Схема — источник истины по именам полей, но не по обязательности и не по
значениям.** `title` помечен `nullable`, а без него оба *arr падают с 500.
У Sonarr `colonReplacementFormat` описан голым `integer` без enum'а.

**Перемежающаяся проверка опаснее падающей.** `checks/06` проходила на
односезонном сериале и валилась на десятисезонном — гонка. Прошедшая проверка
не доказывает работоспособности, если она недетерминирована. Ошибку нашёл
человек руками, а не автоматика.

**Проверка, которая молча смотрит не всё, хуже отсутствующей.**
`04-hardlink.sh` разбирала один файл из скольких угодно, потому что
`docker compose exec` внутри `while read` съедал stdin цикла, — и отчитывалась
зелёным.

# 5. Формат отчёта

Файл `reports/stage-<N>-<краткое-имя>.md`. Коммитится вместе с кодом —
иначе находки испаряются вместе с сессией.

```markdown
# Этап <N>: <название>

**Статус:** завершён | остановлен | завершён с оговорками
**Ветка:** stage/<N>-<имя>
**Дата:**

## Что сделано
Список изменений с путями к файлам.

## Проверки
| Проверка | Результат |
|---|---|
| checks/0X-… | прошла / не прошла |

## Гипотезы, которые подтвердились
Со ссылкой на пункт OPEN-QUESTIONS.md.

## Гипотезы, которые НЕ подтвердились
Что утверждалось, что оказалось. Точный запрос и точный ответ.
Ссылка на пункт OPEN-QUESTIONS.md.

## Стоп-условие (если сработало)
Номер условия из PROCESS.md.
Что именно произошло: запрос, ответ, код, сообщение.
Какой инвариант пришлось бы нарушить для обхода.
Что нужно от человека, чтобы продолжить.

## Открытые вопросы
Новые непроверенные допущения, если появились.
```

**Обязательно приводить точные запросы и ответы,** а не пересказ. «Не
получилось добавить сезон» бесполезно; тело запроса и тело ответа —
достаточно, чтобы понять причину без повторения эксперимента.

---

# 6. Что делать с находками

Каждое подтверждение или опровержение гипотезы **переносится в
`OPEN-QUESTIONS.md`**: подтверждённое уходит в `SPEC.md`, пункт удаляется;
опровергнутое переписывается с фактами.

Файл `OPEN-QUESTIONS.md` существует отдельно от `SPEC.md` именно поэтому:
смешивание проверенного с предполагаемым приводит к тому, что догадка
фиксируется в тестах и становится «требованием».

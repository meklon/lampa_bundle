# Прослеживаемость заказа: состояние в карточке Lampa

**Дата:** 2026-08-03
**Ветка:** `stage/9-traceability`
**Статус:** согласовано, к реализации

## Задача

После заказа фильм или сезон пропадает из виду. Что с ним — искали ли,
нашли ли релиз, качается ли, импортировался ли — узнать с телефона нельзя.
Сегодня это выясняется по логам bridge, очереди и истории Radarr, логам
Prowlarr, состоянию торрента в qBittorrent и файлам внутри контейнера:
пять мест на один вопрос «где мой фильм».

Стек должен отвечать на этот вопрос сам, там же, где заказ делался — в
карточке Lampa.

## Границы

**В скоупе:** фильмы и сериалы, состояние в карточке, снимок при открытии
плюс ручное обновление.

**Вне скоупа:** уведомления (требуют памяти о том, что уже сообщено, а это
состояние); отдельный экран «Мои заказы»; скорость и число сидов из
qBittorrent.

## Главное ограничение

`CLAUDE.md`, список непересматриваемых решений: **«bridge без состояния. Ни
базы, ни очереди, ни повторов, ни трекинга статусов»**.

Отсюда устройство фичи. Bridge ничего не помнит о заказах. Он **спрашивает у
Radarr и Sonarr текущее положение дел в тот момент, когда спросили его**, и
формулирует ответ. Это чтение, а не трекинг: ни кэша, ни фонового опроса, ни
истории. Инвариант остаётся в силе без оговорок.

## Контракт

```
GET /status?tmdb_id=<int>&type=movie|tv
```

Ответ для фильма:

```json
{
  "state": "downloading",
  "label": "Закачивается 44%",
  "detail": "осталось ~3 мин · Zakulise.realnosti.2026.AMZN.WEB-DLRip.AVC",
  "can_order": false
}
```

Ответ для сериала — то же плюс разбивка по сезонам:

```json
{
  "state": "downloading",
  "label": "Сезон 2: закачивается 44%",
  "detail": null,
  "can_order": true,
  "seasons": [
    {"season": 1, "state": "not_ordered", "label": "не заказан"},
    {"season": 2, "state": "downloading", "label": "закачивается 44% · 3 из 10 серий"},
    {"season": 3, "state": "in_library",  "label": "в библиотеке · 10 из 10"}
  ]
}
```

`state` — машинное, для единственного решения плагина: рисовать «Заказать»
или нет. `label` и `detail` — готовый текст.

**Формулировки живут в Python.** Не потому, что так удобнее, а потому что там
на них можно написать тест. В плагине они были бы непроверяемыми, а плагин по
инварианту остаётся тонким.

`can_order` у сериала всегда `true`: другой сезон заказать можно в любой
момент.

## Состояния фильма

Проверяются в этом порядке — от прочитанного напрямую к выведенному.

| Состояние | Как определяется | Текст |
|---|---|---|
| `not_ordered` | по `tmdbId` в Radarr нет | «Заказать» |
| `searching` | в `/command` есть `MoviesSearch`, `status=started`, наш `movieId` в `body.movieIds` | «Ищется релиз…» |
| `stuck` | в `/queue`, есть `errorMessage` или непустые `statusMessages` | «Затык: <сообщение Radarr>» |
| `importing` | в `/queue`, `trackedDownloadState` — импорт | «Импортируется» |
| `downloading` | в `/queue` | «Закачивается 44% · осталось ~3 мин» |
| `in_library` | `hasFile=true` | «В библиотеке · Bluray-576p · 2.3 ГБ» |
| `unmonitored` | файла нет, `monitored=false` | «Снят с наблюдения» |
| `not_found` | файла нет, очереди нет, отслеживается, `lastSearchTime` задан | «При поиске в 13:39 подходящих релизов не нашлось» |
| `waiting` | файла нет, очереди нет, отслеживается, `lastSearchTime` пуст | «Заказан, поиск ещё не запускался» |

**Порядок обязателен и проверяется тестом.** Фильм с `errorMessage` в очереди
должен давать `stuck`, а не бодрое «Закачивается 44%»: показать прогресс там,
где загрузка встала, — это то же самое молчаливое расхождение, против
которого написан весь проект.

### `not_found` — единственный вывод, а не факт

Radarr нигде не записывает «поиск ничего не дал». Проверено: после неудачного
поиска история фильма пуста, а `lastSearchTime` проставлен.

Поэтому формулировка говорит о том, что видно — «искали тогда-то, файла
нет», — а не «релизов не существует». Разница существенная: релиз мог быть
отвергнут профилем качества, мог не подойти по кастомным форматам, мог
появиться минуту спустя.

## Состояния сезона

Те же имена, но считаются по эпизодам сезона, а не по одному файлу. Порядок
проверки — сверху вниз.

| Состояние | Как определяется |
|---|---|
| `not_ordered` | сезон не отслеживается и файлов сезона нет |
| `searching` | в `/command` есть `SeasonSearch` со `status=started`, нашими `seriesId` и `seasonNumber` |
| `monitoring_broken` | сезон `monitored=true`, но **ни один эпизод сезона не отслеживается** |
| `stuck` | в `/queue` есть запись этого сезона с `errorMessage` или `statusMessages` |
| `importing` | в `/queue` есть запись этого сезона в состоянии импорта |
| `downloading` | в `/queue` есть запись этого сезона |
| `in_library` | `episodeFileCount == totalEpisodeCount` и он больше нуля |
| `partial` | `0 < episodeFileCount < totalEpisodeCount` → «5 из 10 серий» |
| `not_found` | файлов нет, очереди нет, у эпизодов сезона задан `lastSearchTime` |
| `waiting` | файлов нет, очереди нет, `lastSearchTime` пуст |

`monitoring_broken` проверяется **раньше** очереди и статистики намеренно:
сломанный мониторинг надо показать, даже если сезон частично скачан раньше.

### Состояние сериала в целом

Верхнеуровневый `state` — это состояние **самого «активного»** сезона по
приоритету:

```
stuck > monitoring_broken > downloading > importing > searching
      > partial > in_library > not_found > waiting > not_ordered
```

`label` при этом называет сезон: «Сезон 2: закачивается 44%». Если ни один
сезон не заказан, состояние сериала — `not_ordered`.

Приоритет отличается от порядка проверки внутри сезона: там важно не
перепутать причину, здесь — показать самое требующее внимания.

`monitoring_broken` — самое ценное здесь. Это ровно тот отказ восьмого этапа:
заказ прошёл, сезон отслеживается, поиск находит семнадцать релизов и не
берёт ни одного, потому что эпизоды выключены. `checks/06` его пропускала, в
интерфейсе он не проявлялся никак.

Баг починен, но починка не гарантирует, что похожее не повторится — от новой
версии Sonarr, от ручной правки в интерфейсе. С этим состоянием стек
**показывает своё расхождение сам**, вместо того чтобы молча ничего не
делать.

## Источники данных

Всё читается у Radarr и Sonarr. Новых связей между компонентами не
появляется, новых ключей в bridge не появляется.

| Что нужно | Откуда |
|---|---|
| фильм, `hasFile`, `monitored`, `lastSearchTime`, `movieFile` | `GET /api/v3/movie` |
| прогресс, остаток, ошибки | `GET /api/v3/queue` |
| идёт ли поиск прямо сейчас | `GET /api/v3/command`, `body.movieIds` |
| сериал, статистика сезонов | `GET /api/v3/series/{id}` |
| мониторинг эпизодов, `lastSearchTime` | `GET /api/v3/episode?seriesId=` |

Имена полей сверены со схемами в `openapi/` и проверены на живом стенде.
`body.movieIds` в `/command` и `lastSearchTime` у `MovieResource` и
`EpisodeResource` — проверены отдельно, потому что от них зависит, будет
состояние фактом или догадкой.

Запросов на один вызов: три для фильма, все внутри compose-сети (к Radarr).
Для сериала — пять, а не четыре: один из них (`Tmdb().tvdb_id()`, трансляция
TMDB→TVDB) уходит во внешний интернет, к `api.themoviedb.org`, а не в
compose-сеть — сериальная ветка `/status` зависит от доступности TMDB.
Таймаут — не единое число: 30 секунд на запрос к Radarr/Sonarr, 15 секунд на
запрос к TMDB.

*Уточнено по факту реализации (этап 9, ревью task-7): в этом абзаце изначально
стояли другие числа — «четыре запроса для сериала», «все внутри compose-сети»
и общий «таймаут 5 секунд». Ни то, ни другое не подтвердилось кодом
(`bridge/app/radarr.py`, `bridge/app/sonarr.py`, `bridge/app/tmdb.py`); см.
`docs/SPEC.md`, раздел `GET /status`.*

## Отказы

**Не ответил — значит не знаем.** Radarr или Sonarr недоступны → `/status`
отвечает ошибкой. Плагин рисует карточку как сегодня: кнопка «Заказать».

**Выдуманных состояний быть не должно.** Особенно `not_ordered` из
недоступности: это подтолкнуло бы заказать то, что уже качается.

Цена ошибки при этом невелика: `/order` идемпотентен, повторный заказ вернёт
`exists`. Проверено `checks/05` и `checks/06`.

## Режимы

**В `dev` эндпоинт работает.** Он только читает у *arr и **не трогает
трекеры**. Запрет `BRIDGE_ENV=dev` касается поиска, здесь его нет. В dev он
даже полезнее: видно, что заказ лёг, а поиск не запускался.

Это отличает `/status` от отменённого счётчика доступности релизов, который
ходил бы на трекеры и в dev был бы запрещён.

## Плагин

Изменения минимальны:

1. при открытии карточки — `GET /status`
2. кнопка «Заказать» заменяется строкой состояния, если `can_order=false`
3. пункт «Обновить» рядом — повторный запрос без выхода из карточки
4. в списке сезонов у каждого сезона — его состояние
5. `/status` не ответил → поведение как сегодня, кнопка «Заказать»

Ни таймеров, ни опроса: снимок при открытии плюс ручное обновление. Таймер
пришлось бы гасить при уходе с карточки, а незакрытый таймер — это утечка и
запросы в пустоту.

## Проверки

### Тесты bridge — на записанных ответах, без сети

- таблица состояний фильма: каждое из девяти из своей фикстуры
- таблица состояний сезона: каждое из десяти
- приоритет при сведении сезонов в состояние сериала
- **порядок проверок**: `stuck` важнее `importing`, `importing` важнее
  `downloading`
- `not_found` против `waiting` — различаются только `lastSearchTime`
- `monitoring_broken`: сезон отслеживается, эпизоды нет
- отказ Radarr → ошибка, **а не состояние**; `not_ordered` не выдумывается
- форматирование: «44%», «3 из 10 серий», размер файла

### `checks/09-status.sh` — против живого стека

Утверждения о совпадении с действительностью, а не о коде ответа:

```
фильм с hasFile=true в Radarr   → /status даёт in_library
фильма нет в Radarr             → not_ordered
```

И воспроизведение восьмого этапа:

```
1. снять мониторинг с эпизодов заказанного сезона (PUT /episode/monitor)
2. /status обязан вернуть monitoring_broken
3. вернуть мониторинг обратно
4. /status обязан вернуть прежнее состояние
```

Проверка искусственно создаёт молчаливый отказ и требует, чтобы стек его
показал.

Плюс: за время вызова `/status` в логах Prowlarr не появилось ни одного
поискового запроса. Эндпоинт обязан оставаться читающим.

## Открытые вопросы

**Аутентификации у bridge нет вообще.** Сегодня по нему можно узнать список
профилей качества. С `/status` любой, кто дотянулся до порта 8000, узнает,
что заказывали и что лежит в библиотеке. CORS от этого не защищает: он
ограничивает браузер, а не `curl`.

В домашней сети это, вероятно, приемлемо, но это осознанное расширение того,
что стек рассказывает о себе непрошеным. Пункт про аутентификацию bridge
идёт в `docs/OPEN-QUESTIONS.md`.

**Как часто `monitoring_broken` срабатывает в жизни** — наблюдать. Если
никогда, состояние всё равно оправдано ценой отказа; если регулярно, это
сигнал искать причину в Sonarr.

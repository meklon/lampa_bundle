# ACCEPTANCE.md

Критерии приёмки по этапам.

Смысл этого файла: критерий успеха не определяется агентом. HTTP 200 и
строчка в логе не являются доказательством. Каждая проверка сформулирована
так, чтобы **упасть**, если оно на самом деле сломано.

Все проверки лежат в `checks/`, возвращают код ≠ 0 при провале, запускаются
поодиночке или через `checks/run-all.sh`.

---

## Этап 1 — инфраструктура

### `01-containers.sh`

- каждый контейнер в состоянии `running`
- Radarr, Sonarr, Prowlarr отвечают `200` на `/api/v3/system/status`
  (`/api/v1/` у Prowlarr) с ключом из `.env`
- qBittorrent отвечает на `/api/v2/app/version` после логина
- bridge отвечает `200` на `/health`

Смысл: «контейнер поднялся» и «сервис работает с нашим ключом» — разные
утверждения. Проверяется второе.

### `02-data-layout.sh`

- каталоги `/data/torrents/{movies,tv}` и `/data/media/{movies,tv}` существуют
- владелец и группа соответствуют `PUID`/`PGID`
- **внутри контейнера Radarr** `stat -c %d /data/torrents` и
  `stat -c %d /data/media` дают одно и то же число устройства

Последнее — главная проверка файла. Она обязана выполняться **внутри
контейнера**, потому что граница монтирования существует именно там. На хосте
пути могут лежать на одной ФС, а в контейнере оказаться разными
монтированиями — и жёсткие ссылки сломаются молча.

## Этап 2 — конфигурация как код

### `03-prowlarr-sync.sh`

- в Prowlarr настроены Apps: Radarr и Sonarr, тест соединения проходит
- `GET /api/v3/indexer` у Radarr возвращает непустой список
- ни один индексатор не был создан в Radarr напрямую

Смысл: проверяется именно **направление** синхронизации. Индексаторы
появились в Radarr, хотя туда их никто не заводил, — значит Prowlarr их
записал.

Пока человек не добавил в Prowlarr ни одного индексатора, проверка
пропускается с явным сообщением, а не считается пройденной.

### Дополнительно, вручную

- повторный запуск `provision/provision.sh` не создаёт дубликатов и не падает
- в Radarr и Sonarr все writer'ы метаданных выключены
- схема переименования соответствует `NAMING.md`

## Этап 3 — конвейер

### `04-hardlink.sh`

- найти импортированный файл в `/data/media`
- `stat -c %h` ≥ 2
- `stat -c %i` совпадает с иноудом файла под `/data/torrents`

Смысл: единственная настоящая проверка главной инфраструктурной ошибки.
Настройка называется «Use Hardlinks instead of Copy», и когда ссылка
невозможна, *arr **молча копирует** — ошибки нет, узнаёшь через месяц по
свободному месту.

### `07-pipeline.sh`

Сквозная проверка без bridge и без сети:

- тестовый торрент добавлен в qBittorrent в категорию `radarr`, состояние 100 %
- Radarr импортировал файл
- файл лежит по **ожидаемому пути** с **ожидаемым именем** согласно `NAMING.md`
- количество жёстких ссылок ≥ 2
- торрент по-прежнему в qBittorrent и раздаётся

Это приёмка минимального конвейера. Терминальный критерий проекта —
именно она, а не «появилось в Kodi».

## Этап 4 — схемы

Проверяется `scripts/check-versions.sh`:

- для каждой схемы в `openapi/` есть запись в `SOURCES.md` с версией и коммитом
- версия схемы совпадает с версией живого инстанса из `/api/v3/system/status`

Расхождение — стоп-условие, не предупреждение.

## Этап 5 — bridge

### `05-bridge-movie.sh`

- `POST /order` с `type: "movie"` возвращает `200` и `status: "queued"`
- фильм присутствует в Radarr: `GET /api/v3/movie` содержит нужный `tmdbId`
- у фильма выставлены ожидаемые `qualityProfileId`, `rootFolderPath`,
  `minimumAvailability`
- **в dev-режиме поиск не запущен:** очередь Radarr пуста, история пуста
- повторный `POST /order` с тем же `tmdb_id` возвращает `200` и
  `status: "exists"` — это успех, не отказ

### `06-bridge-season.sh`

- `POST /order` с `type: "tv"` и номером сезона возвращает `200`
- сериал присутствует в Sonarr с ожидаемым `tvdbId`
- **ровно один сезон** имеет `monitored: true`
- **`monitorNewItems` равно `"none"`**
- в dev-режиме поиск не запущен

Предпоследний пункт — то, из-за чего вообще нужен `monitorNewItems`: без
него заказ одного сезона превращается в подписку на сериал.

### Тесты bridge

`pytest` в `bridge/tests/` на записанных ответах API, без сети.
Обязательные случаи — в `SPEC.md`, раздел контракта, и в
`bridge/tests/README.md`.

## Этап 6 — плагин

Проверяется вручную, автоматизации не поддаётся:

- кнопка появляется в карточке фильма и в карточке сериала
- для сериала предлагается выбор сезона
- в логах bridge виден входящий запрос с **правильным** `tmdb_id` и типом
- уведомление в интерфейсе показывает текст из `detail`
- в исходнике плагина отсутствуют ключи, токены и адреса *arr

Последний пункт проверяется `grep`, а не глазами.

## Разделение checks/ и bridge/tests/

Намеренное, это разные инструменты:

| | `bridge/tests/` | `checks/` |
|---|---|---|
| Что | pytest на записанных ответах | shell + curl + jq + stat |
| Когда | в цикле разработки | между этапами |
| Сеть | не нужна | нужен Docker и ФС |
| Роль | тесты | ворота |

`04-hardlink.sh` проверяет `stat -c %h` и совпадение инодов — pytest этого
сделать не может.
